# SOC Analyst L1 Alert Triage Playbook

## 1. Purpose

This playbook provides a repeatable first-line workflow for reviewing Wazuh alerts, validating available evidence, documenting findings, and escalating suspicious activity.

It is intended for a learning lab and should be adapted to the organization's approved procedures before production use.

## 2. Standard Triage Workflow

### Step 1: Validate the Alert

- Record the alert timestamp and endpoint.
- Record the Wazuh rule ID, severity level, description, and available event fields.
- Confirm that the alert is visible in the Wazuh Dashboard.
- Identify whether the event was generated by controlled lab testing.

### Step 2: Gather Context

- Review related events before and after the alert.
- Check relevant authentication and system logs.
- Identify the affected host, account, source IP, or file path where available.
- Compare the activity with approved maintenance and testing.

### Step 3: Assess the Activity

Classify the event provisionally as one of the following:

- **Expected activity:** Evidence supports an authorized action or controlled test.
- **Suspicious activity:** The event is unexpected or has indicators requiring more investigation.
- **Inconclusive:** Available evidence is insufficient to determine whether the activity is legitimate.

Do not label an event malicious solely because of its severity level.

### Step 4: Decide on Next Steps

- Close or document expected lab activity with supporting evidence.
- Investigate suspicious events and correlate them with additional telemetry.
- Escalate potentially malicious or high-impact events according to the applicable response policy.
- Do not perform disruptive containment actions without appropriate authorization.

### Step 5: Document the Outcome

Record the alert, relevant evidence, investigation steps, assessment, actions taken, and outstanding questions.

## 3. Playbook: Repeated SSH Authentication Failures

**Relevant lab rule:** `100100`, Level 10.

1. Review the alert and identify the source IP, endpoint, targeted username, and timestamp.
2. Inspect the correlated authentication failures.
3. Determine whether the source is local, authorized, or unexpected.
4. Check for subsequent successful logins and other related activity.
5. Establish whether the event corresponds to controlled testing.
6. If unexplained, continue investigation and escalate as required.
7. Record the conclusion and supporting evidence.

**Important lab context:** The observed test source IP was `127.0.0.1`. The validated event was part of a controlled simulation and does not establish a remote attack.

## 4. Playbook: File Modification

**Relevant lab rule:** `550`, Level 7.

1. Identify the modified file and affected endpoint.
2. Review the event timestamp and available file-change details.
3. Determine whether a user, administrator, package update, or approved process explains the change.
4. Compare the change with expected configuration or file contents when possible.
5. Investigate unexplained changes and related events.
6. Escalate if the evidence suggests unauthorized modification.

## 5. Playbook: File Deletion

**Relevant lab rule:** `553`, Level 7.

1. Identify the deleted file and endpoint.
2. Determine whether the deletion was expected.
3. Review available system and audit logs for context.
4. Check whether the deletion affects system integrity or an important service.
5. Preserve relevant evidence and escalate unexplained or high-impact deletions.
6. Restore the file only when appropriate and through an approved recovery process.

## 6. Severity and Escalation

Wazuh severity levels are useful prioritization signals, but severity alone does not determine business impact.

Consider the event's context, affected asset, corroborating evidence, recurrence, and potential consequences. Follow organizational escalation timelines and incident-response policies.

## 7. Minimum Investigation Record

For every investigated alert, record:

- Alert ID or relevant event identifier
- Date and time, including timezone where known
- Endpoint and affected asset
- Rule ID, level, and alert description
- Relevant source IP, account, or file path
- Supporting events and evidence
- Analyst assessment and confidence
- Actions taken and approvals, where applicable
- Escalation status and outstanding questions
- Final disposition

## 8. Lab Limitations

This lab validates three specific detection outcomes: repeated SSH authentication failures, file modification, and file deletion. It does not demonstrate comprehensive threat coverage, automated response, or a production incident-management process.
